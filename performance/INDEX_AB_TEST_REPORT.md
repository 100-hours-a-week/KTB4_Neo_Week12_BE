# 인덱스 A/B 성능 테스트 결과

## 1. 결론

동일한 애플리케이션, 데이터, JMeter 시나리오에서 인덱스만 추가한 결과, 첫 게시글 목록의 대표 중앙값은 **2,675ms에서 1,359ms로 49.2% 감소**했고 처리량은 **9.5% 증가**했다. 일반 댓글과 중간 규모 댓글의 중앙값도 각각 **19.9%, 21.4% 감소**했다.

반면 깊은 페이지 조회는 중앙값이 **4,180ms에서 4,742ms로 13.4% 악화**됐다. 인덱스는 정렬과 전체 테이블 스캔을 줄였지만 `OFFSET 80000`이 앞의 80,020개 인덱스 항목을 읽고 버리는 구조까지 해결하지는 못한다. 따라서 B 단계는 인덱스 효과가 분명히 확인됐지만, 깊은 페이지와 꼬리 지연시간은 추가 개선 대상으로 남았다.

## 2. 테스트 조건과 비교 원칙

- 실행 위치: 개발자 Mac 로컬 환경
- 애플리케이션: Spring Boot 컨테이너 1개
- 데이터베이스: MySQL 8.4.11 컨테이너
- 캐시: Redis 7 컨테이너
- 데이터: 사용자 10,000명, 게시글 100,000개, 댓글 500,000개
- 활성 데이터: 사용자 9,500명, 게시글 95,000개, 댓글 450,000개
- JMeter: 스레드 30, ramp-up 30초, 본 테스트 180초
- 비교 횟수: A/B 각각 3회
- 각 실행 전 동일한 워밍업 수행
- A: PK와 FK용 기본 인덱스만 존재
- B: Flyway V2로 복합 인덱스 6개 추가
- 대표값: 일회성 흔들림을 줄이기 위해 3회 결과의 지표별 중앙값 사용
- 성공 조건: B 3회 모두 HTTP 오류 0건, DB/Redis/애플리케이션 healthy, Flyway V2 성공, 6개 인덱스와 컬럼 순서 확인

JMeter의 30 스레드는 정확히 “동시 사용자 30명”과 같지는 않다. 각 스레드가 응답을 기다린 뒤 다음 요청을 보내므로, 이 결과는 **동시에 작업을 반복하는 가상 사용자 30개가 만든 폐쇄형 부하**로 해석한다.

## 4. 6개 복합 인덱스별 실행 계획 분석

`EXPLAIN ANALYZE` 시간은 단일 쿼리의 실행 계획 검증값이다. 캐시 상태와 실행 순서의 영향을 받으므로 JMeter 응답시간과 직접 같지는 않지만, 스캔 행 수와 정렬 제거 여부를 통해 인덱스가 의도대로 사용되는지 확인할 수 있다.

| 인덱스 | 목표 쿼리 | 인덱스 추가 전 | 인덱스 추가 후 | 판단 |
|---|---|---|---|---|
| `idx_users_email_deleted (email, deleted)` | 로그인/이메일로 활성 사용자 조회 | 사용자 10,000행 테이블 스캔, 15.3ms | covering index로 1행 조회, 0.0186ms | 스캔 범위가 10,000→1행. 실행 계획상 약 99.9% 감소 |
| `idx_users_nickname_deleted (nickname, deleted)` | 닉네임 중복/활성 사용자 조회 | 10,000행 테이블 스캔, 1.99ms | covering index로 1행 조회, 0.00354ms | 중복 확인 비용과 데이터 증가 민감도를 크게 낮춤 |
| `idx_posts_deleted_created_at (deleted, created_at DESC)` | 활성 게시글 최신순 목록 | 첫 페이지: 100,000행 스캔·정렬, 126ms. 깊은 페이지: 41.7ms | 첫 페이지: 20개 인덱스 행, 0.0421ms. 깊은 페이지: 80,020개 인덱스 행, 8.16ms | 첫 페이지는 스캔과 정렬 제거. 깊은 페이지는 약 80.4% 감소했어도 큰 OFFSET은 유지 |
| `idx_posts_user_created_at (user_id, created_at)` | 사용자의 특정 시점 이후 게시글 | FK 인덱스로 10행 조회 후 필터, 3.08ms | 복합 범위/covering 조회 9행, 1.12ms | 실행 계획상 약 63.6% 감소. 사용자별 최신/기간 조회에 적합 |
| `idx_comments_post_created_at (post_id, created_at)` | 게시글 댓글 시간순 조회 | FK 인덱스 조회 후 별도 정렬. 일반 2.39ms, 중간 1.83ms | 인덱스 순서로 바로 조회. 일반 0.0465ms, 중간 0.561ms | 정렬 제거. 실행 계획상 각각 약 98.1%, 69.3% 감소 |
| `idx_comments_user_deleted_post (user_id, deleted, post_id)` | 사용자가 여러 게시글에 작성한 활성 댓글/권한 확인 | 동일 쿼리의 저장된 A 실행 계획 없음 | covering range scan 사용 확인 | 신규 인덱스 사용 0.0188ms, 관련 인덱스 배제 시 500,000행 스캔 293ms. 단, 기존 A에는 `user_id` FK 인덱스가 있었으므로 99.99%를 실제 A/B 개선율로 주장할 수는 없음 |

여섯 번째 인덱스를 추가하자 MySQL은 `user_id`로 시작하는 신규 인덱스가 FK 검사를 지원할 수 있다고 판단해 기존 자동 생성 단일 FK 인덱스를 제거했다. 따라서 인덱스 중복 저장 비용을 남기지 않으면서 `user_id + deleted + post_id` 조건을 더 구체적으로 지원한다.

실행 계획 검증 쿼리는 일부 컬럼만 선택해 covering index 효과가 크게 나타난다. 실제 JPA API는 더 많은 컬럼, 엔티티 연관관계, JSON 직렬화를 포함하므로 위의 99%대 DB 단일 쿼리 감소율이 API 응답시간에 그대로 반영되지는 않는다. 이것이 JMeter 개선 폭이 실행 계획 개선 폭보다 작은 주된 이유다.

## 5. 사용자 체감 해석

- 첫 게시글 페이지 중앙값은 약 **1.32초 단축**됐다. 사용자가 목록을 처음 열거나 새로고침할 때 “상당히 답답함”에서 “개선됐지만 아직 즉각적이지는 않음”으로 바뀔 가능성이 크다.
- 일반 댓글 중앙값은 약 **0.34초**, 중간 댓글은 약 **0.36초 단축**됐다. 반복적으로 댓글을 여는 사용자에게는 반응성이 조금 더 안정적으로 느껴질 수 있다.
- 처리량이 시나리오별 약 **7.6~9.5% 증가**해 같은 로컬 자원에서 처리 가능한 요청 수가 늘었다.
- 첫 페이지 p95가 여전히 약 **3.97초**, 댓글 p95가 약 **3.74~3.93초**다. 사용자 20명 중 1명꼴로 수 초를 기다릴 수 있어 꼬리 지연은 여전히 좋지 않다.
- 깊은 페이지는 중앙값 약 **4.74초**, p95 약 **7.40초**로 실제 서비스에서는 페이지가 멈춘 듯 느껴지고 이탈을 유발할 수 있는 수준이다.

이 수치는 EC2의 실제 용량이나 인터넷 지연을 예측하는 값이 아니라, 동일한 로컬 조건에서 코드 변경의 상대 효과를 판단하는 값이다. 운영 EC2/RDS에 부하를 주지 않았으므로 비용과 배포 안정성에는 영향을 주지 않는다.

## 6. 일부 수치가 개선되지 않은 이유

1. **큰 OFFSET의 구조적 한계**  
   `OFFSET 80000 LIMIT 20`은 복합 인덱스가 있어도 앞선 80,000개를 건너뛰어야 한다. 깊은 페이지는 커서 기반 페이지네이션(`created_at`, 동률 처리용 PK)을 도입해야 근본적으로 개선된다. 단, 이는 API 계약을 유지할 방법을 먼저 설계해야 한다.

2. **DB 외 구간이 API 응답시간을 지배**  
   JPA 엔티티 생성, 연관관계 추가 조회, 트랜잭션, 커넥션 대기, JSON 직렬화가 포함된다. SQL이 빨라져도 이 구간이 병목이면 전체 개선율은 제한된다.

3. **30개 요청의 자원 경쟁과 꼬리 지연**  
   CPU, DB 커넥션 풀, 컨테이너 자원을 동시에 경쟁한다. 평균과 p50은 좋아졌지만 댓글 p95가 소폭 나빠진 것은 인덱스 자체의 실패라기보다 로컬 스케줄링과 대기열 변동 가능성이 크다.

4. **로그인 표본과 비밀번호 검증 비용**  
   로그인은 실행당 표본이 적고 BCrypt 같은 비밀번호 검증 비용이 DB 조회보다 훨씬 클 수 있다. 이메일 인덱스의 효과는 실행 계획에서 명확하지만 로그인 API 지연시간만으로는 분리해 측정하기 어렵다.

5. **캐시 워밍과 실행 순서**  
   InnoDB buffer pool, JVM JIT, OS 캐시는 각 실행에서 완전히 동일하지 않다. 그래서 단 한 번의 최고 결과 대신 3회 대표 중앙값을 사용했다.

6. **인덱스의 쓰기 비용**  
   이번 테스트는 조회 중심이다. 6개 복합 인덱스는 INSERT/UPDATE/DELETE 때 추가 갱신과 저장공간을 요구한다. 향후 쓰기 시나리오도 별도로 측정해야 전체 성능의 손익을 판단할 수 있다.

## 7. B 단계 완료 판정과 다음 개선 후보

B 단계 완료 조건은 충족했다.

- Flyway V2가 정상 적용됐고 재기동 후에도 스키마 검증이 성공했다.
- 의도한 6개 복합 인덱스와 컬럼 순서를 MySQL에서 확인했다.
- `ANALYZE TABLE`을 수행했고 `EXPLAIN ANALYZE`로 실제 인덱스 사용을 확인했다.
- A/B 모두 동일 데이터와 동일 JMeter 계획으로 3회 비교했다.
- B 3회의 HTTP 오류율은 모두 0%였다.
- 기존 API를 변경하지 않았으며 테스트는 로컬에서만 실행했다.

다음 우선순위는 깊은 게시글 페이지의 커서 기반 페이지네이션 검토, SQL/JPA 쿼리 수 측정을 통한 N+1 확인, 커넥션 풀 대기시간과 JVM/DB CPU 계측, 댓글 p95 재검증, 조회와 별도로 인덱스 추가 전후의 쓰기 부하 비교다.
